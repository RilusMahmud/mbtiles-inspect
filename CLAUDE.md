# CLAUDE.md

Project context and rules for Claude Code working on `mbtiles-inspect`.

## What this project is

Read `SPEC.md` first. Short version: a Go CLI + TUI for inspecting `.mbtiles`
files. Subcommands for scripting/CI, TUI for interactive use. Single static
binary, pure Go, no CGO.

## Ground rules

1. **Read `SPEC.md` before any non-trivial change.** If a change conflicts with
   the spec, stop and surface the conflict — don't silently deviate.
2. **Pure Go only.** No CGO. This means `modernc.org/sqlite`, not
   `mattn/go-sqlite3`. Cross-compilation must work without a C toolchain.
3. **Read-only on user files.** Never open mbtiles in write mode. SQLite
   `mode=ro` in the connection string.
4. **No network.** This tool operates on local files. No HTTP clients, no
   "download fixtures from S3" tricks.
5. **Errors are wrapped with context** using `fmt.Errorf("…: %w", err)`. No
   bare `return err` from anywhere except trivial leaf functions.
6. **Stable output formats.** `--json` output is part of the public API.
   Changes to JSON shape need a version bump and a note in CHANGELOG.

## Coding standards

- Go 1.22+ idioms. Use `slices`, `maps`, `cmp` stdlib packages.
- Keep packages small and single-purpose. The layout in `SPEC.md` is the
  target — don't collapse packages into `internal/util/`.
- Public types/functions get doc comments. Private ones get them when
  non-obvious.
- Table-driven tests. One `t.Run` per case. Use `testify/require` only if it's
  already in the module; otherwise stdlib `testing` + `t.Fatalf`.
- No global state. Pass dependencies explicitly. Logger is a `*slog.Logger`
  passed into constructors.
- Format with `gofmt -s` and lint with `go vet ./...`. `golangci-lint run`
  before declaring a task done.

## Project conventions

- CLI subcommands live in `cmd/mbtiles-inspect/`, one file per subcommand
  (`info.go`, `gaps.go`, etc.). `main.go` only does cobra root setup.
- Each subcommand file exposes a `newXxxCmd() *cobra.Command`.
- TUI sub-models are one file per tab in `internal/tui/`. Each implements the
  bubbletea `tea.Model` interface (`Init`, `Update`, `View`).
- All user-facing strings live next to the code that emits them. No i18n.
- Color output goes through `lipgloss`. Respect `NO_COLOR` env var and
  `--no-color` flag.

## Build, test, run

```sh
go build -o bin/mbtiles-inspect ./cmd/mbtiles-inspect
go test ./...
go vet ./...
golangci-lint run
```

Use `make` if a Makefile exists; otherwise raw commands above. Don't introduce
build-system dependencies (Bazel, Mage, etc.) without discussion.

## Test fixtures

Test mbtiles files live in `testdata/`. They're tiny (KB scale) and
deterministically generated by `testdata/gen.go`. To regenerate:

```sh
go run ./testdata/gen.go
```

Don't commit large fixtures. Don't rely on real-world mbtiles for tests.
Generated fixtures cover: complete file, file with gaps, file with TMS
y-convention, file with XYZ y-convention, corrupt-tile file, non-mbtiles
SQLite file.

## Common tasks

### Adding a new subcommand

1. Create `cmd/mbtiles-inspect/<name>.go` with `newXxxCmd()`.
2. Register in `main.go`'s `init()` or root-cmd setup.
3. If it produces structured output, add `--json` support via `internal/report`.
4. Add an integration test that runs the binary against a fixture and checks
   stdout/exit code. See `cmd/mbtiles-inspect/info_test.go` for the pattern.

### Adding a new TUI tab

1. Create `internal/tui/<name>_tab.go` implementing `tea.Model`.
2. Add the tab to the top-level model's tab list and key bindings.
3. Tab data should come from the same `internal/mbtiles` reader the
   subcommands use — don't duplicate query logic.

### Touching slippy-map math

`internal/tiles/slippy.go` has reference unit tests with known-good values.
Don't change behavior without updating tests. The math is in the spec
(`SPEC.md` → "Gap detection algorithm"); copy formulas verbatim.

## Things to avoid

- Don't pull in heavy frameworks. No Cobra alternatives, no Bubble Tea
  alternatives. We picked these.
- Don't add caching layers. SQLite + the OS page cache is enough.
- Don't add a config file. Flags + env vars only.
- Don't add telemetry, analytics, update-check, or any phone-home behavior.
- Don't reformat or "tidy up" unrelated files in a PR. Keep diffs minimal.
- Don't write markdown lists in commit messages. Imperative one-liner +
  optional body.

## Definition of done for any task

- Code compiles, `go vet` clean, `golangci-lint` clean.
- Tests added or updated. `go test ./...` passes.
- If a subcommand was added/changed: human-readable and JSON output both
  exercised by tests.
- README updated if public CLI surface changed.
- No TODOs left in changed files unless tracked in an issue.

## If you get stuck

Surface the blocker. Don't paper over it with a `TODO` and keep going. If the
spec is ambiguous, propose two options and ask. If a dependency is missing a
feature, say so before working around it.
